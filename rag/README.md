# Навигатор по регламентам: поисковое ядро

Хакатон «ИИ в системе управления МФТИ», трек 04 «Навигатор сотрудника по непрочитанным регламентам» (кейсодатель ФЭУ).

Сотрудник пишет задачу своими словами («потерял пропуск», «нужно взять пару дней за свой счёт»). Ядро:

1. находит подходящий регламент, а внутри него нужные пункты;
2. возвращает короткий пошаговый алгоритм только по тексту регламента; у каждого шага есть ссылка на пункт, а также, если это есть в тексте, кто выполняет шаг, срок и документ;
3. отвечает «В регламентах не найдено», если ничего не подходит, и задаёт уточняющий вопрос, если запрос неоднозначный.

Зависимостей нет, нужен только Node.js 22+. Модели подключаются по желанию через OpenAI-совместимый API: внешний, LM Studio, Ollama, vLLM. Без моделей ядро тоже работает: тогда шаги берутся дословно из пунктов.

## Быстрый старт

```sh
# Node 22+ (на этой машине: export PATH=/f/tools/node-v22.20.0-win-x64:$PATH)
node cli.js ingest fixtures/docs --out data/fixtures-index.json
node cli.js ask "потерял пропуск, что делать" --index data/fixtures-index.json
node cli.js ask "как оформить командировку" --index data/fixtures-index.json --json   # полный JSON

RAG_INDEX=data/fixtures-index.json node server.js      # API на http://127.0.0.1:8787
npm test                                               # 38 тестов
npm run eval:fixtures && npm run eval:holdout          # метрики
```

Пример ответа CLI:

```
Документ: «Инструкция о пропускном режиме на территории кампуса»
1. При утрате или порче пропуска его владелец в течение одного рабочего дня сообщает об этом в бюро пропусков.  (п. 10)
   кто: владелец; срок: в течение одного рабочего дня
2. Для восстановления пропуска владелец подаёт в бюро пропусков заявление на выдачу дубликата.  (п. 11)
   кто: владелец; документ: заявление на выдачу дубликата
...
[режим: extractive]
```

## Архитектура

```
файлы (.txt .md .json .docx .pdf .html)
  │  src/extract.js   docx: свой ZIP-ридер + восстановление автонумерации Word
  │                   pdf: pdftotext, если есть, иначе встроенный ридер текстового слоя
  ▼
src/parser.js     структура регламента: 1. / 1.1. / 2.3.4. / а) б) / 1) 2) / I. II. /
  │               «Раздел N» с перезапуском нумерации / приложения (прил.1/2.3) / заголовки
  ▼
src/store.js      пункты -> фрагменты (подпункты вклеены в пункт, но цитируются отдельно)
  │               -> один JSON-индекс (+ векторы, если задан EMBED_BASE_URL)
  ▼
ask(question)
  ├─ src/retrieve.js
  │    запрос: стемминг Snowball (src/stemmer.js), стоп-слова, разговорные синонимы
  │    (src/synonyms.js: «потерял» -> «утрата», «академ» -> «академический отпуск»),
  │    морфологические соседи («согласовать» ~ «согласование»)
  │    этап 1, документ: RRF из BM25 по документу, BM25 лучших пунктов,
  │                      покрытия слов запроса и (если есть) косинуса векторов
  │    фильтр «не найдено»: покрытие ниже порога или совпали только общие слова
  │    этап 2, пункты:   BM25 со статистикой внутри документа + векторы, RRF;
  │                      выбор раздела, где лежит процедура
  ├─ src/generate.js
  │    LLM (LLM_BASE_URL): строгий JSON по схеме, повтор с json_object и без него,
  │                        если сервер схему не поддерживает
  │    без LLM или при ошибке: экстрактивный режим, шаги = пункты дословно
  └─ src/verify.js   детерминированная проверка каждого шага:
       цитата есть в контексте, слова шага покрыты текстом пункта (>= 60%),
       все числа и числительные шага есть в пункте, отрицание не перевёрнуто.
       Шаг без опоры отбрасывается (или помечается, verifier=flag).
       Поля who/deadline/form без опоры в пункте удаляются, сам шаг остаётся.
       Если LLM-шаги не прошли все, ответ собирается экстрактивно.
```

Почему так:

- Сначала документ, потом пункты. Сотруднику нужен один регламент, а не смесь фрагментов из пяти. Во втором этапе BM25 считается по пунктам одного документа, поэтому слова из названия, которые есть в каждом его пункте, перестают перевешивать.
- Решение «не найдено» принимается до вызова LLM. Оно основано на покрытии слов запроса, поэтому вопрос не по теме не доходит до модели и не получает выдуманный ответ.
- Проверка шагов детерминированная, без второй модели. Её можно объяснить жюри и показать в интерфейсе, что именно не сошлось.
- Индекс хранится в JSON. Его можно посмотреть и сравнить, нативные модули не нужны (`node:sqlite` в Node 22 ещё экспериментальный). На 480 документах (6300 пунктов) индекс загружается за 0,17 с, запрос обрабатывается примерно за 15 мс без моделей.

## API

`ask(question, opts)` из `src/index.js`:

```js
const rag = require('./src');
await rag.ingest(['corpus/'], { out: 'data/index.json' });
const a = await rag.ask('как получить аванс на командировку', { indexPath: 'data/index.json' });
```

Опции: `indexPath | store`, `mode` (`auto` | `llm` | `extractive`), `verifier` (`drop` | `flag`), `maxSteps` (8), `minSupport` (0.6), `minCoverage` (0.55), `debug`, а также `llmBaseUrl/llmModel/llmApiKey` и `embedBaseUrl/embedModel/embedApiKey`, которые перекрывают переменные окружения.

Форма ответа:

```jsonc
{
  "question": "...",
  "not_found": false,
  "message": null,                       // "В регламентах не найдено." при not_found
  "document": { "id": "komandirovki", "title": "...", "url": null, "file": "komandirovki.txt", "source": "/doc/komandirovki" },
  "documents": [ ... ],                  // все документы, на которые есть ссылки
  "steps": [{
    "n": 1,
    "text": "Работник подаёт в бухгалтерию заявление на выдачу аванса ...",
    "cites": [{ "doc": "komandirovki", "docTitle": "...", "clause": "2.5", "label": "п. 2.5",
                "quote": "полный текст пункта", "anchor": "cl-2-5" }],
    "who": "работник", "deadline": null, "form": "заявление на выдачу аванса",   // если есть в тексте
    "verified": true, "support": 1
  }],
  "rejected_steps": [ { "text": "...", "issues": ["low_support:0.20"], ... } ],
  "clarifying_question": null,           // или вопрос
  "mode": "extractive",                  // llm | llm+extractive | extractive
  "candidates": [ { "id": "...", "title": "...", "score": 0.049, "coverage": 1 } ],
  "warnings": [], "diagnostics": { ... }
}
```

От LLM требуется ровно такой JSON: `{document, steps:[{text, cites:["D1:2.5"], who?, deadline?, form?}], not_found, clarifying_question?}`. API дополняет его цитатами, якорями и результатом проверки.

HTTP (`server.js`, CORS включён, `CORS_ORIGIN` по умолчанию `*`):

| Метод | Путь | Что |
|---|---|---|
| POST | `/ask` | `{"question": "...", "mode"?: "...", "verifier"?: "flag"}` → ответ выше |
| GET | `/doc/:id` | весь регламент по пунктам: `{id, title, nodes:[{id, anchor, kind, label, text, heading}]}`, для панели «показать источник» |
| GET | `/doc/:id?format=html&hl=2.5,2.6` | готовая HTML-страница с якорями и подсветкой пунктов |
| GET | `/docs` | список регламентов в индексе |
| GET | `/health` | число документов и пунктов, дата индекса, настроены ли LLM и эмбеддинги |

`cites[].anchor` из `/ask` совпадает с `nodes[].anchor` из `/doc/:id`. Интерфейс может открыть документ и прокрутить к пункту: `/doc/propusk?format=html&hl=10#cl-10`.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_BASE_URL` | не задана: экстрактивный режим | OpenAI-совместимый endpoint, например `http://localhost:1234/v1` (LM Studio) или `http://localhost:11434/v1` (Ollama) |
| `LLM_MODEL` | `local-model` | имя модели |
| `LLM_API_KEY` | пусто | ключ, если нужен |
| `LLM_JSON_MODE` | `schema` | `schema` → `object` → без формата; `object` или `none`, если сервер не понимает `json_schema` |
| `LLM_TIMEOUT_MS` | `120000` | таймаут запроса к LLM |
| `EMBED_BASE_URL` | не задана: только BM25 | endpoint `/v1/embeddings`, нужен и при `ingest`, и при `ask` |
| `EMBED_MODEL` | `text-embedding-bge-m3` | модель должна совпадать при `ingest` и `ask`, иначе векторы не используются (будет предупреждение) |
| `EMBED_API_KEY` | пусто | ключ |
| `RAG_INDEX` | `data/index.json` | индекс для `ask` и сервера |
| `RAG_SYNONYMS` | `synonyms.json` рядом с индексом | дополнительные синонимы |
| `RAG_PDFTOTEXT` | `pdftotext` из PATH | путь к pdftotext |
| `RAG_PDF_BUILTIN` | не задана | `1`: не вызывать pdftotext, читать PDF встроенным ридером |
| `PORT`, `HOST`, `CORS_ORIGIN` | `8787`, `127.0.0.1`, `*` | сервер |

Node 22 сам читает `.env`: `node --env-file=.env server.js`.

## Результаты оценки

Данные: 8 тестовых регламентов в `fixtures/docs/`. Это синтетические тексты в стиле локальных актов, не настоящие документы МФТИ. Запуск 07.11.2026, режим `extractive` (LLM и эмбеддинги не подключены), `npm run eval:fixtures` и `npm run eval:holdout`.

| Метрика | `eval-questions.json` (29 вопросов) | `eval-holdout.json` (20 вопросов) |
|---|---|---|
| doc hit@1 | 100% (22/22) | 81,3% (13/16) |
| doc hit@3 | 100% | 100% |
| clause recall (ожидаемые пункты среди процитированных) | 98,9% | 68,8% |
| context recall (ожидаемые пункты в контексте) | 100% | 78,1% |
| ложные «не найдено» | 0/22 | 2/16 |
| точность «не найдено» на вопросах без ответа | 100% (5/5) | 75% (3/4) |
| неоднозначные: задан уточняющий вопрос | 2/2 | — |
| стресс-тест проверки: отклонено испорченных шагов | 305/305 (100%) | 193/195 (99,0%) |
| ложные отклонения корректных шагов | 0/64 | 0/40 |
| задержка ответа | p50 1 мс, max 20 мс | p50 1 мс, max 19 мс |

Как читать эти цифры:

- На `eval-questions.json` поиск настраивался: синонимы, веса, правила выбора раздела. Это оценка на обучающих данных, она завышена.
- `eval-holdout.json` написан после настройки, на нём ничего не подбиралось. Это честная оценка на новых формулировках. Первый прогон дал те же 81,3% / 100% / 75%, clause recall был 71,9%; после следующих общих правок он стал 68,8%. Ошибки: «оформление поездки в Новосибирск» ушло в регламент об отпусках, потому что слово «командировка» в вопросе не встречается; «остаток денег» и «потратил больше, чем дали» получили «не найдено», потому что в регламенте написано «остаток неизрасходованного аванса» и «перерасход»; «пропуск на автомобиль» нашёлся в инструкции о пропусках, хотя про автомобили там ничего нет.
- Стресс-тест проверки шагов: из каждого принятого шага делаются испорченные варианты: выдуманный шаг, изменённое число, ссылка на пункт вне контекста, перевёрнутое отрицание, текст из другого регламента. Проверка должна отклонить испорченные варианты и пропустить исходный шаг. Пропущены 2 случая из 195: число 7 совпало с номером цитируемого пункта 7, и один шаг из другого регламента оказался лексически близок.
- Доля отклонённых сгенерированных шагов в экстрактивном режиме равна 0% по построению: шаги и есть текст пунктов. Эта метрика имеет смысл только в режиме LLM, а его на реальной модели не запускали: на этой машине не отвечали ни `localhost:1234`, ни `localhost:11434`. Путь LLM проверен тестами на поддельном OpenAI-совместимом сервере: строгий JSON, отклонение выдуманного шага, откат на экстрактивный режим, повтор без `json_schema`, недоступный сервер.

Подробности по каждому вопросу сохраняются в `eval/results/*.json`; запуск с `--verbose` выводит их в консоль.

## Скорость

Замер 11.11.2026, ноутбук, Node 22, без модели: ответ собирается из дословных пунктов (`mode: extractive`). Время модели и время получения вектора вопроса сюда не входят, они зависят от того, какая модель подключена.

Оба замера сняты подряд на одной машине. На маленьком корпусе цифры плавают от запуска к запуску: повторный прогон «после» дал p50 1,46 мс на ×1 и 482 запроса в секунду, на ×10 и ×50 — те же 1,6 и 3,8 мс.

Что изменилось:

- BM25 хранит обратный индекс: для каждого слова список пунктов, где оно встречается. Вопрос обходит только списки своих слов, а не все пункты подряд.
- Поиск пунктов внутри выбранного документа считается по тому же индексу, отдельные индексы на каждый документ больше не строятся. Наборы слов по каждому пункту и документу не хранятся, отсюда меньше памяти.
- Близкие по форме слова («согласова» / «согласован») ищутся не по всему словарю, а среди слов с тем же началом из пяти букв; результат для слова запоминается.
- Сравнение с векторами идёт одним циклом по сплошному массиву.

Результаты поиска при этом не изменились: выдача по 129 вопросам на трёх индексах (без векторов, тестовые регламенты, с векторами BGE-M3) совпала с прежней байт в байт. То же закреплено тестами в `test/perf.test.js`: новый BM25 сверяется с простым перебором на случайных данных, поиск близких слов — с полным проходом по словарю.

Что осталось медленным: с векторами время растёт вместе с числом пунктов, потому что вопрос сравнивается с каждым пунктом (на ×10 это около 17 мс из 19). На ×50 с векторами замер не делался; по пропорции это около 90 мс на вопрос. Если корпус вырастет до тысяч документов, понадобится приближённый поиск по векторам.


## Входные данные и повторная загрузка 11.11

Поддерживаются:

- `.txt`, `.md` (UTF-8 или Windows-1251, определяется автоматически);
- `.docx`: текст, таблицы (строка → «ячейка | ячейка») и автонумерация Word. Номера «2.3.» в Word часто не набраны в тексте, а заданы списком; ридер восстанавливает их из `numbering.xml`;
- `.pdf` с текстовым слоем: `pdftotext`, если он есть (в Git for Windows он есть в `mingw64/bin`), иначе встроенный ридер (Flate, object streams, ToUnicode, Identity-H);
- `.html`;
- `.json`: массив или `{"documents": [...]}` с полями `id`, `title`, `content|text|body`, `url`, `group`.

Не поддерживаются, нужна конвертация:

```sh
# .doc / .rtf / .odt -> .docx
soffice --headless --convert-to docx --outdir corpus/ raw/*.doc
# сканы без текстового слоя -> PDF с текстом
ocrmypdf -l rus scan.pdf scan-ocr.pdf
```

Метаданные можно передать через `manifest.json` в той же папке: `[{"file": "komandirovki.docx", "id": "kom", "title": "...", "url": "https://..."}]`. Понимаются и формы `{"documents": [...]}` и `{"file.docx": {...}}`. Без манифеста id берётся из имени файла, название берётся из первых строк документа («Положение о ...», «Порядок ...», «Регламент ...»).

Порядок действий, когда придут данные:

1. Сложить файлы в отдельную папку, например `corpus/feu/`. Если есть `.doc` или сканы, сконвертировать их командами выше.
2. Проверить разбор: `node cli.js ingest corpus/feu --out data/index.json` выводит число документов и пунктов. Если у документа 0–2 пункта при большом тексте, нумерация не распознана; это видно в `GET /doc/:id`.
3. С эмбеддингами: задать `EMBED_BASE_URL` и `EMBED_MODEL` перед `ingest` и использовать ту же модель при `ask`. Без них поиск работает на BM25.
4. Добавить синонимы предметной области в `data/synonyms.json` рядом с индексом (сокращения ФЭУ, разговорные названия процедур): `[["аванс подотчёт", "авансовый отчёт"], [["за свой счёт"], "без сохранения заработной платы"]]`. Строка задаёт слова, каждое из которых сравнивается по стему; массив задаёт целые фразы.
5. Собрать вопросы сотрудников в формате `fixtures/eval-questions.json` и запустить `node eval/run-eval.js --questions <файл> --index data/index.json --verbose`.
6. Перезапуск сервера не нужен: индекс перечитывается, когда меняется файл.

## Ограничения

- Без LLM шаги дословно повторяют пункты регламента: они длинные и не переформулированы, зато точны. Короткие формулировки даёт режим LLM, а проверка шагов не пропускает отсебятину.
- Поиск лексический: BM25, стемминг, синонимы. Если вопрос и регламент описывают одно и то же разными словами («остаток денег» и «неизрасходованный аванс»), документ находится плохо. Помогают эмбеддинги (`EMBED_BASE_URL`, например BGE-M3) и словарь синонимов. На этих данных эмбеддинги не оценивались.
- Решение «не найдено» эвристическое: оно основано на покрытии слов запроса. Вопрос о подвиде того, что есть в регламенте («пропуск на автомобиль» при инструкции о пропусках людей), может получить ответ из близкого документа. В режиме LLM модель может вернуть `not_found`, но окончательно это не проверено.
- Проверка шагов лексическая. Она ловит выдуманные шаги, числа, отрицания и ссылки вне контекста, но не ловит перестановку смысла теми же словами (например, «A передаёт B» вместо «B передаёт A»).
- Тестовые регламенты синтетические и аккуратно свёрстаны. Реальные документы (колонтитулы, сноски, таблицы, «Приложение к приказу» в шапке) парсер ещё не видел.
- Встроенный PDF-ридер рассчитан на простой текстовый слой. Для сложной вёрстки нужен `pdftotext`.
